# Cinematic Production Execution Contract

Status: **OWNER-DIRECTED CONTROLLING PRODUCTION INSTRUCTION**  
Date: 2026-09-05  
Companion issue: #2787  
Compass traversal companion: `docs/COMPASS_CINEMATIC_PRODUCTION_TRAVERSAL_LEDGER.md`

This contract prevents repeated failure to enter the actual video-production toolchain. Diamond Gate has already produced multiple cinematic/video artifacts. Future rooms must not behave as though video production is an unknown capability simply because one repository API cannot itself encode media.

For the current Compass single-master successor, this contract defines production law and the traversal ledger defines the exact execution sequence. If a broad instruction here could be read as one monolithic task, the ledger controls the decomposition.

## Governing rule

Once the cinematic class, storyboard, source truth, and correction scope are frozen, production must follow the smallest precedent-congruent path to a complete cinematic source and then to a verified master.

The governing sequence is:

`ACCEPTED FILM FLOOR -> DIRECT BOUNDED CORRECTIONS -> CAPTURE-READY CINEMATIC SOURCE -> FUNCTIONAL RENDERER GATE -> REPRESENTATIVE FRAMES -> FULL CAPTURE -> ENCODE -> VERIFY -> COMMIT MASTER -> THIN PLAYER -> FOCUSED OWNER REVIEW`

Do not substitute:

`GITHUB_CONTENTS_API_CANNOT_ENCODE_VIDEO -> VIDEO_PRODUCTION_BLOCKED`

or:

`RENDERER_NOT_YET_PROVEN -> DO_NOT_CONSTRUCT_COMPLETE CINEMATIC SOURCE`

for the correct staged capability boundary.

## Execution-capability inventory and hard gate

A production room must inventory the available execution surface early so it does not invent infrastructure blindly. Check for at least:

- Chromium/Chrome or another approved browser renderer;
- FFmpeg or another approved media encoder;
- Node/Python or an equivalent bounded orchestration runtime when needed;
- local/container filesystem access for transient frames/render products;
- connected GitHub binary-blob/tree/commit capability or an equivalent lawful repository-ingress method.

Tool locations may vary by room. **Probe; do not assume.**

However, About precedent resolves the sequencing ambiguity:

- renderer/encoder availability does **not** block construction of the complete self-contained capture-ready cinematic source;
- the functional browser renderer becomes a hard gate only after `CAPTURE_READY_SOURCE_COMPLETE`;
- that hard gate is T7 in `docs/COMPASS_CINEMATIC_PRODUCTION_TRAVERSAL_LEDGER.md`;
- if T7 fails, stop at `CAPTURE_READY_SOURCE_COMPLETE / FRAME_RENDER_BLOCKED` rather than inventing more production layers or reopening the cinematic architecture.

A functional renderer PASS means a real controlled test frame was produced and decoded, not merely that an executable exists.

## Normal pre-rendered production path

For browser-authored cinematics, the normal implementation is:

`HTML/CSS/JS SOURCE -> CHROMIUM FRAME CAPTURE -> FFMPEG H.264/AAC MASTER -> SHA/DECODE/FAST-START CHECKS -> GITHUB BLOB/TREE/COMMIT`

This is an established direct-production class. It does not require Codespaces and does not require GitHub Actions as agent-execution transport.

For the current Compass successor, the exact traversal from source recovery through owner review is T0-T13 in `docs/COMPASS_CINEMATIC_PRODUCTION_TRAVERSAL_LEDGER.md`.

## Precedent meaning

Established About, Chapter One, and Compass cinematic precedents prove the governing production pattern. Do not repeatedly reopen precedent after the class has been resolved.

- **About precedent** demonstrates direct bounded cinematic construction before browser/perceptual qualification, preservation of an accepted floor, and surgical replacement of deficient visual objects with the smallest authoritative source donors.
- **Chapter One precedent** demonstrates delivery of an actual encoded H.264/AAC master with exact media verification and bounded repository scope.
- **Compass precedent** demonstrates proportional qualification and owner inspection for noninteractive cinematic work.

Precedent is an execution constraint, not historical context. When a prior cinematic already solved the same production purpose with a smaller bounded surface, reuse that method before adding architecture.

## About-congruence law

For bounded cinematic corrections:

1. start from the complete accepted floor;
2. correct one deficient visual/semantic beat at a time;
3. preserve all non-target behavior;
4. use the smallest authoritative source component that produces recognizable source truth;
5. make each accepted correction the next floor;
6. construct the complete cinematic before expanding qualification;
7. treat browser/perceptual evidence as the next evidence boundary, not a reason to keep adding pre-render machinery.

Wrapper-on-wrapper production architecture, full destination-application embedding, late-source readiness systems, and whole-film reconstruction are rejected unless a named ledger state proves that no smaller precedent-congruent method can perform the exact required operation.

## Anti-stall laws

Once storyboard, source truth, production class, and ledger state are resolved, a construction room must not:

- search broadly for an old MP4 merely because GitHub's text/content API does not encode video;
- request, create, recommend, or wait for Codespaces;
- use GitHub Actions as agent-execution transport unless separately and explicitly authorized;
- restart canonical intake, routing, governance, or precedent review that has already closed;
- rebuild a rejected historical runtime when the target is a pre-rendered master;
- treat destination/product runtimes as playback or manufacturing dependencies when they are only source donors;
- add a wrapper, bridge, readiness system, transport, or framework before identifying the exact unsolved operation;
- call branch creation or source inspection "film progress";
- claim that a film branch has advanced unless the branch is observably ahead of its base with concrete changed paths and the claimed state has the evidence required by the traversal ledger;
- execute two consecutive construction increments that add preparation/machinery without yielding a more complete visible cinematic candidate. The second such increment must stop with `ANTI_REINVENTION_CHECK_REQUIRED`.

Before adding new cinematic machinery, ask:

`DID ABOUT OR ANOTHER ACCEPTED CINEMATIC PRECEDENT ALREADY SOLVE THIS SAME PRODUCTION PURPOSE WITH A SMALLER SURFACE?`

If yes, reuse that pattern. If no, identify the exact unsolved operation and the ledger state in which it belongs.

## Progress-truth invariant

The following language is prohibited unless repository/artifact state proves it:

- "advanced the film";
- "built the master";
- "candidate produced";
- "implementation complete";
- equivalent completion/progress claims.

Minimum evidence for any production-progress claim:

1. exact branch/base identity;
2. exact ledger state reached;
3. exact changed paths or artifact identity;
4. that state's required `PASS_EVIDENCE` is present;
5. no protected-surface mutation outside the bounded scope.

Additional status boundaries:

- branch only: `BRANCH_CREATED / PRODUCT_CONSTRUCTION_NOT_STARTED`;
- complete self-contained source, no rendered frame yet: `CAPTURE_READY_SOURCE_COMPLETE`;
- functional renderer unavailable after T7 probe: `CAPTURE_READY_SOURCE_COMPLETE / FRAME_RENDER_BLOCKED`;
- encoded media not yet committed: do not claim `MASTER_CANDIDATE_PRODUCED`;
- only after T11 commits the verified media with custody evidence: `MASTER_CANDIDATE_PRODUCED`.

## Stop rule

A room may stop before producing the master only at a concrete ledger boundary with a deterministic blocker. The blocker report must name:

- ledger state;
- exact missing capability or failed acceptance condition;
- exact probe/evidence that established it;
- why no already-authorized precedent-congruent method can perform that operation;
- precise artifact boundary reached;
- applicable `FAIL_STOP_CODE`.

"No native checkout in the GitHub connector," "GitHub API cannot encode MP4," "Codespace seems easier," or "browser evidence is not yet available" are not sufficient reasons to stop construction before T6 when the complete capture-ready cinematic source can still be built through bounded repository operations.

At T7 and later, a tested renderer/encoder failure is a legitimate production blocker and must not be converted into permission to redesign the cinematic.
