Structure Track · Interfaces

Where systems meet.

Interfaces are the structured meeting points between systems, people, domains, tools, and claims. They determine what can pass, what must be translated, what fails at the edge, and how contact is confirmed.

Track standing

Interfaces is one Structure track in the sixteen-track Laws constellation. It is not the same as Constraints, Boundaries, or Governance.

  • Constraints define what limits action.
  • Interfaces define where systems meet and exchange.
  • Boundaries define what separates domains and prevents leakage.
  • Governance defines how rules stay active under pressure.
Interface signature

A usable interface has a contract, translation rule, failure surface, and handshake. Without those, contact becomes ambiguity.

Interfaces Section 01

Interface Contract

An interface contract defines what may enter, what may leave, what shape the exchange must take, and what responsibility each side accepts.

Input shape Output shape Obligation Compatibility
Platform

The interface contract prevents confusion at the meeting point. It says what each side is allowed to send, receive, require, reject, and preserve.

  • Name what crosses the interface.
  • Name who owns the input and who owns the output.
  • Define what counts as valid exchange.
  • Reject silent compatibility assumptions.
Engineering

In engineering terms, the interface contract maps to schema, API contract, data type, event shape, method signature, precondition, postcondition, and version compatibility.

  • Declare required and optional fields.
  • Version the contract when meaning changes.
  • Validate input before processing it.
  • Return explicit errors instead of ambiguous failure.
Evidence

Evidence for an interface contract requires recoverable definitions and observable enforcement. A contract that exists only in memory is not stable enough.

  • Strong evidence: schema, tests, version history, validation failures, compatibility records.
  • Useful evidence: API docs, interface receipts, consumer compatibility notes.
  • Failure mode: behavior depends on undocumented assumptions.
  • Boundary: a contract is not proven just because both sides currently work once.

Interfaces Section 02

Translation

Translation is the work of preserving meaning across an interface. The same signal can become false if it changes shape without preserving meaning.

Meaning preservation Adapter logic Semantic mapping
Platform

Translation is not just changing format. It is preserving meaning as a claim, instruction, signal, responsibility, or value crosses from one system into another.

  • Preserve the meaning, not just the label.
  • Do not let simplification erase obligation.
  • Do not let format conversion hide uncertainty.
  • Mark losses, assumptions, and substitutions explicitly.
Engineering

Translation maps to adapters, serializers, deserializers, normalization layers, migration transforms, data mappers, unit conversion, and semantic compatibility rules.

  • Test round-trip meaning where possible.
  • Track lossy transformations.
  • Separate display formatting from semantic conversion.
  • Version translation rules when mappings change.
Evidence

Evidence for translation requires showing that the receiving side understands the same meaning the sending side intended.

  • Strong evidence: mapping tests, round-trip checks, migration comparison, semantic acceptance cases.
  • Useful evidence: transformation logs, adapter tests, conversion fixtures.
  • Failure mode: field names match while meaning diverges.
  • Boundary: translation can be valid even when imperfect if loss is declared and bounded.

Interfaces Section 03

Failure Surface

The failure surface is where interface weakness becomes visible. Bad interfaces often fail at the edge, not in the center.

Error shape Fallback No-match Edge condition
Platform

An interface must define how failure appears. If failure is silent, the user or downstream system becomes responsible for discovering the broken edge.

  • Name invalid input instead of accepting it silently.
  • Make rejection understandable.
  • Define what happens when no match exists.
  • Prevent edge failure from corrupting the receiving system.
Engineering

Failure surface maps to error codes, exception handling, fallback policy, no-match records, timeout behavior, retry rules, validation rejection, and degraded-mode behavior.

  • Distinguish invalid, missing, ambiguous, expired, and unsupported inputs.
  • Return actionable errors.
  • Protect downstream state when interface validation fails.
  • Log edge-case failures for contract revision.
Evidence

Evidence for failure-surface quality requires failure records, not just success-path demonstrations.

  • Strong evidence: negative tests, no-match logs, malformed input tests, fallback records.
  • Useful evidence: error taxonomy, rejection samples, timeout behavior records.
  • Failure mode: successful demo hides broken edge behavior.
  • Boundary: a safe rejection is often better than a permissive corrupted acceptance.

Interfaces Section 04

Handshake

The handshake confirms that contact occurred, the exchange was understood, and responsibility transferred or remained where it belongs.

Confirmation Acknowledgment Transfer state Closure
Platform

The handshake prevents false completion. It confirms whether the other side received, understood, accepted, rejected, or deferred the exchange.

  • Confirm receipt.
  • Confirm meaning.
  • Confirm transfer of responsibility.
  • Confirm whether the exchange is complete or still open.
Engineering

Handshake maps to acknowledgments, response codes, commit confirmation, idempotency keys, delivery receipts, state transitions, callback results, and closure signals.

  • Use explicit acknowledgment rather than assumed success.
  • Prevent duplicate action with idempotency controls.
  • Track whether the receiving side committed or rejected the exchange.
  • Keep retry behavior aligned with handshake state.
Evidence

Evidence for handshake quality requires proof of receipt, interpretation, acceptance, and closure state.

  • Strong evidence: receipt logs, acknowledgment events, commit records, state transition history.
  • Useful evidence: callback records, retry logs, duplicate-prevention records.
  • Failure mode: sender assumes success because no failure was returned.
  • Boundary: receipt does not always mean acceptance; both states must be distinguishable.

Canonical Interface Laws

Contact without contract creates ambiguity.

Interfaces hold structure by making exchange legible. A system becomes fragile when the meeting point has no contract, no translation rule, no failure surface, or no handshake.

Canonical Law Interface Contract Law

Every stable exchange requires a declared contract for what can cross, in what form, and under whose responsibility.

Canonical Law Translation Preservation Law

Meaning must survive the interface, or the exchange becomes distortion rather than transfer.

Signature Legible exchange

Valid input, preserved meaning, explicit failure, and confirmed contact.

Failure Pattern Silent edge failure

The interface appears to work while ambiguity, loss, or corruption moves downstream.
