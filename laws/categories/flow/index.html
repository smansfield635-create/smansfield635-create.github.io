Laws Category · Flow

What moves.

Flow reads motion through signal, response, return, and transfer. It asks what is moving, where it is going, what it changes, and how it is handed from one state to the next.

Category role

Flow is the category for movement. It does not only ask whether something exists. It asks how it travels, repeats, reacts, and transfers across a system.

  • Signals show what is being emitted or received.
  • Feedback shows what returns and changes the next state.
  • Cycles show what repeats, returns, and compounds.
  • Handoffs show how movement transfers between domains.

Flow Track 01

Signals

What is emitted, received, noticed, missed, amplified, or ignored.

Emission Reception Noise Signal quality
Platform

Signals are how movement becomes visible. A system can only respond to what it can receive, distinguish, and interpret.

  • What is being sent?
  • Who or what receives it?
  • What is signal and what is noise?
  • What disappears before it can be acted on?
Engineering

Signals map to event emission, telemetry, detection thresholds, routing, noise filtering, state notification, and observable change.

  • Declare the signal source.
  • Declare receiver and route.
  • Measure signal strength, delay, distortion, or loss.
  • Classify whether the signal triggers a state change.
Evidence

Evidence for Signals requires records that show an emitted signal was received, missed, changed, amplified, or filtered.

  • Strong evidence: event logs, telemetry, timestamped signal record, receiver state.
  • Useful evidence: alert history, routing trace, missed-signal report, noise analysis.
  • Failure mode: reaction is expected without a reliable received signal.

Flow Track 02

Feedback

What returns from output into the next input.

Return signal Amplification Damping Adjustment
Platform

Feedback is the return path of consequence. It tells the system whether output is stabilizing, escalating, correcting, or degrading the next state.

  • What came back?
  • What changed because it came back?
  • Did the return amplify or reduce pressure?
  • Was the system able to adjust?
Engineering

Feedback maps to output-to-input return, correction loops, amplification, damping, error propagation, control response, and state adjustment.

  • Track output state.
  • Track returned signal.
  • Measure correction, amplification, or damping.
  • Classify whether the loop stabilizes or destabilizes.
Evidence

Evidence for Feedback requires a trace showing that output returned and influenced the next state.

  • Strong evidence: loop trace, before/after state, returned signal, correction record.
  • Useful evidence: response logs, error reports, adjustment notes, control records.
  • Failure mode: repeated output is called feedback without a return path.

Flow Track 03

Cycles

What repeats, returns, synchronizes, and compounds.

Recurrence Rhythm Feedback Renewal
Platform

Cycles are not repetition alone. A cycle is a return pattern that changes the system each time it comes back.

  • What returns?
  • How often does it return?
  • What does each return change?
  • Does the cycle renew, escalate, or degrade?
Engineering

Cycles map to recurrence, interval, amplitude, phase, feedback, state change, Fibonacci synchronization posture, and NEWS directional reading.

  • Track recurrence and interval.
  • Compare timing, amplitude, and phase.
  • Classify feedback carryover.
  • Use the Cycles page for the Fibonacci Synchronization Metric and NEWS Protocol explanation.
Evidence

Evidence for Cycles requires repeated passes with enough timing and state data to distinguish a real cycle from isolated recurrence.

  • Strong evidence: timestamped passes, interval table, phase notes, state-change record.
  • Useful evidence: event sequence, recurrence history, feedback trace, renewal record.
  • Failure mode: one repeated theme is treated as a measured cycle without pass data.

Flow Track 04

Handoffs

How movement transfers from one domain, actor, state, or phase to another.

Transfer Custody Timing Continuity
Platform

Handoffs decide whether movement survives transfer. A good handoff preserves meaning, timing, responsibility, and enough context for the next holder to continue without distortion.

  • What is being transferred?
  • Who gives it?
  • Who receives it?
  • What must be preserved through transfer?
Engineering

Handoffs map to custody transfer, interface transition, state passing, queue movement, ownership change, protocol exchange, and context preservation.

  • Declare sender and receiver.
  • Preserve state and context.
  • Record timing and acceptance.
  • Detect dropped, duplicated, delayed, or corrupted transfer.
Evidence

Evidence for Handoffs requires proof that transfer occurred and the receiving side could continue with the required context intact.

  • Strong evidence: transfer receipt, custody record, sender/receiver trace, accepted state.
  • Useful evidence: queue logs, handoff notes, transition history, continuity checks.
  • Failure mode: the object moves, but meaning or responsibility is lost.
